*(2026-09-21, mode nocturne autonome. Zone choisie par `recommendZone()` en rotation, seule zone
jamais examinée depuis la création de l'outil le 2026-09-19 — cf. `docs/referentiel/points-fragiles.md`.
Consultation SMART-CONSO-TOKEN faite avant ce raisonnement : `full_repo_scope`, verdict
"avertissement souple", négociable, confirmé et enregistré.)*

## 1. Survol — les fichiers réellement concernés

La mécanique de fatigue traverse 7 fichiers, chacun avec une responsabilité claire et distincte :

| Fichier | Rôle exact |
|---|---|
| `lib/simulation.ts` | Modèle numérique de base : `Needs.fatigue`, taux par personnage (`residentProfiles`), `advanceNeeds()` (montée/récupération), seuil de bascule vers l'intention `sleep` (`fatigue>=68`), rendu visuel continu (paupières lourdes, `faceExpression()`). |
| `lib/daynight.ts` | Horloge jour/nuit (constantes nommées `DAY_ROUNDS`/`NIGHT_ROUNDS`/`MIDNIGHT_OFFSET`, prédicats `isNight()`/`isMidnight()`/`phaseOf()`) + `fatigueRateMultiplier()` (×3 la nuit, jamais sur la récupération). |
| `lib/life.ts` | Mémoire persistée de la dette de sommeil : `sleptThisNight` (flag par personnage, jamais un compteur cumulable). |
| `lib/drama.ts` | Constantes numériques partagées pour les à-coups ponctuels (`emotionalShockFatigue`, `rejection.fatigue`). |
| `app/api/lia/route.ts` | Orchestration par tour : narration (crépuscule/tombée de nuit/nuit blanche/aube), application du malus de dette de sommeil (+28), remise à zéro du flag à l'aube. |
| `lib/lia.ts` | Bloc de prompt "FATIGUE ET REGISTRE" : au-delà de 50 (et plus encore 68), amplifie l'aspérité de chaque personnage à sa manière (Lia sèche/cassante, Noé dans le brouillard/dispersé) — jamais de la douceur. |
| `docs/referentiel/regles-du-temps.md` + `parametres.md` | Documentation de référence des seuils et de la logique. |

**Verdict du survol : cette répartition en 7 fichiers n'est PAS de la dette.** C'est exactement le
même découpage que le reste du projet applique déjà partout (moteur numérique / horloge / mémoire
persistée / constantes de drame / orchestration / prompt / documentation) — le vérifier explicitement
avant d'accuser quoi que ce soit d'"empilé" (garde-fou `trottoirGranted`, cf. Article 19). Aucune
proposition de fusionner ces fichiers ne suit.

## 2. Zoom — deux trouvailles concrètes

### Trouvaille 1 — Confiance : CONFIRMÉE. Le seuil 68 existe en double, sans source commune.

Le seuil qui fait basculer un personnage en sommeil est écrit UNE fois dans le code
(`lib/simulation.ts:96`, `if (needs.fatigue >= 68) return "sleep"`) — mais le même chiffre est
RETAPÉ, en toutes lettres, dans le bloc de prompt de `lib/lia.ts` ("dès que state.needs.fatigue
dépasse 50, et plus encore au-delà de 68"). Rien ne relie ces deux emplacements : ce sont deux
occurrences indépendantes du même nombre.

Aujourd'hui, ça fonctionne, parce que personne n'a encore rééquilibré ce seuil. Mais si un futur
rééquilibrage change `68` dans `lib/simulation.ts` (pour accélérer ou ralentir l'endormissement),
rien n'avertira qu'il faut aussi retaper le nouveau chiffre dans le prompt de `lib/lia.ts` — les deux
resteraient synchronisés par chance, pas par construction. C'est exactement le type de risque que
`lib/daynight.ts` a déjà résolu pour l'horloge jour/nuit (constantes nommées `DAY_ROUNDS`,
`MIDNIGHT_OFFSET`, jamais un chiffre en dur répété) : la fatigue n'a jamais reçu le même traitement.

*(Vérifié explicitement : `docs/referentiel/parametres.md` cite aussi "68" en toutes lettres, mais
c'est un DOCUMENT de référence humain — c'est son rôle d'énoncer la valeur en prose. Ce n'est pas la
même chose qu'un second exemplaire du chiffre à l'intérieur du CODE/PROMPT lui-même.)*

### Trouvaille 2 — Confiance : CONFIRMÉE. Pas de prédicat `isDawn()`, contrairement à `isNight()`/`isMidnight()`.

`lib/daynight.ts` exporte déjà des fonctions nommées pour "est-ce la nuit ?" (`isNight()`) et
"est-ce minuit ?" (`isMidnight()`) — exactement pour que le reste du code n'ait jamais à retaper la
formule brute. Mais "est-ce l'aube ?" n'a jamais reçu son propre nom : l'expression brute
`cyclePosition(nextStory.round)===0&&nextStory.round>0` est tapée à l'identique DEUX fois dans
`app/api/lia/route.ts` (ligne ~1364, narration de l'aube ; ligne ~1539, remise à zéro du flag de
dette de sommeil) — jamais un `isDawn(round)` exporté depuis `lib/daynight.ts`, alors que c'est
exactement le même besoin que les deux prédicats déjà écrits juste à côté.

Vérifié : les deux copies sont aujourd'hui identiques et correctes (pas de bug actif). C'est
seulement l'absence d'une source unique qui les rend fragiles à une future modification — quelqu'un
qui changerait un jour la condition dans un seul des deux endroits (par exemple pour gérer un cas
particulier) romprait la synchronisation sans avertissement.

## 3. Ce qui est déjà bien construit (pour ne pas donner une impression fausse)

- `lib/daynight.ts` est un modèle du genre : constantes nommées, prédicats exportés, commentaires
  qui expliquent le POURQUOI de chaque chiffre (y compris une vraie anecdote de bug trouvé en
  lançant l'outil, pas seulement en le lisant).
- La séparation "taux passif × multiplicateur jour/nuit" vs "chocs ponctuels additifs" (jamais
  modulés par l'heure) est une distinction propre, documentée, et cohérente partout où elle
  s'applique.
- Le mécanisme de dette de sommeil (`sleptThisNight`) est un simple flag jamais cumulable — décision
  assumée explicitement contre une mécanique de compteur qui aurait pu s'aggraver indéfiniment.

## 4. Ce qui n'est PAS proposé (et pourquoi)

- Fusionner les 7 fichiers en un seul "module fatigue" : casserait un découpage déjà cohérent avec
  le reste du projet (Article 19).
- Rendre le seuil 68 configurable dynamiquement à l'exécution : aucun besoin de jeu ne le demande
  aujourd'hui — ajouterait de la complexité sans bénéfice concret (Article 0 : jamais de complexité
  gratuite).

## 5. Questions de calibrage préparées pour le réveil

1. **[Calibrage] Faut-il corriger la Trouvaille 1 (seuil 68 dupliqué) ?**
   - Option A (recommandée) : extraire une constante nommée unique (ex. `FATIGUE_SLEEP_THRESHOLD =
     68` dans `lib/simulation.ts`), puis injecter sa valeur dans le texte du prompt au moment de sa
     construction (comme le fait déjà `moveReason`, cf. CLAUDE.md Article 10) plutôt que de la
     retaper en dur — élimine le risque de divergence future, sans changer le comportement actuel.
   - Option B : laisser tel quel, et se fier à la vigilance manuelle lors d'un futur rééquilibrage.
   - Option C : documenter explicitement le risque dans `points-fragiles.md` sans corriger
     maintenant (déjà fait par ce rapport), à corriger seulement au moment d'un vrai rééquilibrage du
     seuil.

2. **[Calibrage] Faut-il corriger la Trouvaille 2 (pas de `isDawn()`) ?**
   - Option A (recommandée) : ajouter `export function isDawn(round) { return cyclePosition(round)
     === 0 && round > 0; }` dans `lib/daynight.ts`, puis remplacer les deux occurrences dans
     `route.ts` — changement mécanique, à risque quasi nul, cohérent avec le patron déjà établi.
   - Option B : laisser tel quel (le risque réel est faible tant que personne ne modifie qu'une
     seule des deux copies).

3. **[Alignement de compréhension] Le format de ce premier passage convient-il ?**
   - Ce rapport est volontairement court (2 trouvailles concrètes plutôt qu'une longue liste de
     signaux faibles) — est-ce le bon niveau de profondeur pour un "vrai passage", ou une prochaine
     zone devrait-elle creuser plus large (plus de fichiers, plus de trouvailles candidates avant
     filtrage) ?
